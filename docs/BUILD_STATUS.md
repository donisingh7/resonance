# Resonance — Build Status

Last updated: 2026-09-28 (S6 / R5 — recruiter-ready end-to-end dashboard + workflow orchestration, mock provider)

## Implemented

**Backend (FastAPI, `backend/app/`)** — all S1–S5 endpoints unchanged, plus:
- **New: `GET /projects`** — lists all projects (id, name, description,
  status, created_at), sorted by `created_at`. Backs the Streamlit project
  picker so a demo user never has to paste a project ID manually.
- **New: `GET /projects/{project_id}/overview`** — returns a
  `ProjectOverview`: real counts (assets, processed/failed/pending),
  modality breakdown, intelligence/questionnaire/report/PDF availability,
  a deterministic `overall_pipeline_status` + `current_stage` +
  `next_recommended_action`, and `blockers`/`warnings`. Every field is
  derived from already-persisted data — **no progress percentage is ever
  computed or fabricated**.
- **New: `POST /projects/{project_id}/workflow/run`** — synchronously runs
  whichever pipeline steps are missing, in order: process any never-attempted
  asset, (re)generate project intelligence if missing/failed/outdated,
  generate a questionnaire only if none exists yet for the current
  intelligence, generate a report only if none exists yet for the current
  (intelligence, questionnaire) pairing. Returns a `WorkflowRunResult`
  describing exactly what happened. Safe to click repeatedly: already-current
  steps are skipped, not redone, and an existing questionnaire (including
  manual edits) is never regenerated by this endpoint.
- **New: `POST /projects/{project_id}/assets/{asset_id}/retry`** — re-runs
  processing for one asset. Byte-for-byte the same call as
  `POST .../process` (calls `processing.process_asset()` directly); it exists
  as a separate route purely so the UI can offer an explicit "Retry" action
  next to a failed asset. Inherits the existing idempotent overwrite
  behavior (deterministic `uuid5(asset_id, provider)` result id).

**ProjectOverview model (`backend/app/models/overview.py`)**
`project_id, project_name, total_assets, assets_by_modality,
processed_assets, failed_processing_assets, pending_processing_assets,
latest_intelligence_id, intelligence_status, active_provider,
questionnaire_available, latest_questionnaire_id, report_available,
latest_report_id, pdf_available, overall_pipeline_status, current_stage,
next_recommended_action, blockers, warnings`. `overall_pipeline_status` is
one of a fixed `StageStatus` enum: `not_started, ready, in_progress,
partial, completed, blocked, failed`. `active_provider` is copied from the
latest intelligence result's `provider` (e.g. `"mock"`) — `None` until
intelligence has been generated at least once, rather than assumed.

**Overview derivation (`backend/app/services/overview.py`)** — a fixed,
readable cascade (first matching rule wins):
| Condition | `overall_pipeline_status` | `current_stage` |
|---|---|---|
| zero assets | `not_started` | `upload_assets` |
| some assets never processed | `ready`/`in_progress` | `process_assets` |
| all attempted processing failed | `blocked` | `process_assets` |
| processed assets exist, no intelligence yet | `ready` | `generate_intelligence` |
| latest intelligence `status == "failed"` | `failed` | `generate_intelligence` |
| intelligence exists but new processing results aren't reflected in it | `partial` | `generate_intelligence` |
| intelligence ready, no questionnaire yet | `ready` | `generate_questionnaire` |
| latest questionnaire `status == "failed"` | `partial` | `generate_questionnaire` |
| intelligence ready, no report yet | `ready` | `generate_report` |
| latest report `status == "failed"` | `failed` | `generate_report` |
| everything present and completed | `completed` | `done` |

`intelligence_is_outdated()` (also used by `workflow.py`) detects the
"new processing results exist since intelligence was last generated" case
by diffing completed processing-result ids against the intelligence's own
`source_result_ids` — a real, data-driven check, not a timestamp heuristic.

**WorkflowRunResult model (`backend/app/models/workflow.py`)**
`project_id, started_at, finished_at, stages_attempted, stages_completed,
stages_skipped, asset_processing_successes, asset_processing_failures,
intelligence_id, intelligence_action, questionnaire_id,
questionnaire_action, report_id, report_action, warnings, overview`.
`*_action` fields are one of `generated | reused | updated | skipped`, so a
caller (or the Streamlit UI) can show exactly what the run did rather than
guessing from before/after diffs.

**Workflow orchestration (`backend/app/services/workflow.py`, S6)** — a
single synchronous function, **not** a queue or background worker:
1. Every asset with no `ProcessingResult` yet is processed via the existing
   `processing.process_asset()`; a per-asset exception is caught so one bad
   asset never stops the run — it's recorded in `asset_processing_failures`
   and the loop continues (mirrors `processing.py`'s own internal handling,
   applied one level up for orchestration-level safety).
2. Intelligence is regenerated only if missing, failed, or outdated (per
   `overview.intelligence_is_outdated()`); otherwise reused as-is.
3. A questionnaire is generated only if **none exists yet for the current
   intelligence** — this endpoint never regenerates an existing
   questionnaire, specifically so a second "Run Remaining Pipeline" click
   can never silently discard a manual edit. Regenerating a questionnaire
   on purpose remains a separate, explicit action via
   `POST .../questionnaires` in the Questionnaire tab.
4. A report is generated only if none exists yet for the current
   (intelligence, questionnaire) pairing; if a questionnaire was generated
   *after* an earlier report ran without one, the report is regenerated
   once to link it (`report_action: "updated"`).
5. The final `ProjectOverview` is attached to the result, so callers get a
   fresh status snapshot without a second request.

**Frontend (Streamlit, `frontend/app.py`, fully reorganized)** — now a
project picker followed by six tabs for the active project, instead of one
long scrolling page of disconnected controls:
- **Project picker**: create a new project, select an existing one from
  `GET /projects` (name + short id), or open by pasting a full project id.
  A "🧪 Mock mode active" banner appears whenever the active project's
  latest intelligence used `MockAIProvider`, explaining plainly that all
  AI-derived content is deterministic placeholder output, not real
  analysis — shown once at the top, not just per-record captions.
- **Overview tab**: prominent "🚀 Run Remaining Pipeline" button (calls the
  workflow endpoint, shows a summary of what happened, then reruns);
  pipeline status with an icon, current stage, next recommended action,
  asset/processed/pending/failed metrics, modality breakdown, intelligence/
  questionnaire/report/PDF availability, and all blockers/warnings.
- **Assets tab**: upload, a per-asset expander showing filename/modality/
  ingestion status/processing status/technical metadata, a
  Process/Retry/Reprocess button depending on state, and the full
  `ProcessingResult` once available.
- **Intelligence tab**: generate/regenerate button (never auto-triggered by
  opening the tab), all S4 sections, a "MockAIProvider output" notice, and
  a collapsed list of earlier runs.
- **Questionnaire tab**: unchanged S5 generate/edit/save flow.
- **Executive Report tab**: unchanged S5 generate/view/risk-flags/evidence/
  PDF-download flow.
- **New Evidence tab**: an Evidence Explorer over the latest intelligence
  run's evidence list, filterable by category, source filename, and asset
  id (multiselects), showing category/statement/source/asset id/result
  id/excerpt per item — reads only already-stored evidence, never
  re-derives or invents a snippet.
- All backend calls go through shared `api_get`/`api_post`/`api_put`
  helpers that return `None` on a connection failure, paired with
  `show_backend_error()` so every failure path renders one clear message
  (e.g. "Could not reach the backend while trying to generate the
  report...") instead of ever surfacing a raw stack trace or an unhandled
  exception in the UI.

## Known limitations

- **All AI-derived content across the whole pipeline remains
  `MockAIProvider` deterministic placeholder output** — S6 adds no new AI
  content, only orchestration and presentation around what S3–S5 already
  produce. The Streamlit "Mock mode active" banner and every
  `mock_provider_output` risk flag continue to make this explicit.
- `overall_pipeline_status`/`current_stage` are a fixed rule cascade, not a
  weighted scoring model — e.g. a project with 1 failed and 9 completed
  assets still reads `completed` once intelligence/questionnaire/report
  exist, with the failure surfaced only as a `warnings` entry, not a
  blocking status. This is a deliberate simplicity choice (see task scope:
  "do not fabricate progress percentages"), not an oversight.
- Workflow orchestration is a single synchronous HTTP call — a project with
  many never-processed assets will make the `POST .../workflow/run` request
  take proportionally longer (no background job, no streaming progress).
  Acceptable at demo scale; would need a real job/queue system for a large
  batch, which is explicitly out of scope through at least S7. `workflow.py`
  has no state of its own — nothing to clean up or leak if a client
  disconnects or the server restarts mid-run; whatever completed before
  that point stays persisted normally via the same idempotent per-resource
  writes, and the next run simply picks up wherever it left off.
- The Evidence Explorer only shows evidence from the **latest** intelligence
  run for the active project, not an aggregate across every historical run
  — matches "the current analysis," not a full audit log across
  regenerations (no history/versioning of intelligence exists yet to browse
  regardless).
- `GET /projects` reads every `project.json` in `data/projects/` per
  request — fine at demo scale, same file-scan trade-off already noted for
  asset/result listing; no pagination or search, as scoped.
- No authentication, no database, no queues, no containerization/deployment.
- No automated test suite — verified via one manual smoke pass (see below),
  plus a Streamlit `AppTest` headless run exercising all six tabs.

## Smoke-tested this phase

One practical recruiter-demo pass, backend started locally (`.venv`), full
flow exercised via scripted HTTP calls against a running instance, using a
fresh project with a TXT, a PNG, and a deliberately corrupt "PDF":
- Project create/load; `GET /projects` lists it.
- Overview on a brand-new empty project: `not_started`, `upload_assets`,
  a `no_assets`-style blocker — correct before any upload.
- After uploading 3 assets: overview correctly shows 3 total/3 pending and
  stage `process_assets`.
- **`POST .../workflow/run` (first run)**: processed the TXT and PNG
  successfully, recorded the corrupt-PDF failure without stopping;
  generated intelligence, questionnaire, and report in sequence (all
  `*_action: "generated"`); final embedded overview reports
  `overall_pipeline_status: "completed"` and `pdf_available: true`.
- PDF downloaded successfully (valid `%PDF-` header) using the report id
  the workflow run returned.
- Evidence Explorer data source (the latest intelligence's evidence list)
  verified non-empty with every `asset_id` matching a real uploaded asset.
- Questionnaire manually edited (`PUT`) to prepend `[EDITED BY USER]` to a
  question's text.
- **Retry**: confirmed the corrupt-PDF asset's processing result id is
  unchanged after `POST .../retry` (overwrite, not a duplicate) and still
  correctly reports `status: "failed"`.
- **`POST .../workflow/run` (second run)**: intelligence, questionnaire,
  and report all reported `*_action: "reused"` with unchanged ids;
  `GET` list endpoints confirmed exactly one intelligence/questionnaire/
  report record each after two runs — **no uncontrolled duplication**; the
  manual questionnaire edit was confirmed still present after the second
  run, proving the orchestration did not silently overwrite it.
- Existing individual controls re-verified unaffected: direct
  `POST .../intelligence` regeneration and direct per-asset
  `POST .../process` still work standalone.
- **Streamlit**: booted and served its initial page with no server-side
  exceptions; additionally, the full script was run headlessly via
  Streamlit's `AppTest` framework with an active project pre-populated with
  a completed pipeline (intelligence + edited questionnaire + report + PDF)
  to exercise all six tabs' rendering code paths (not just the empty
  "no project selected" branch a plain page load would hit) — zero
  exceptions across all 6 tabs.
- Not re-tested this phase: audio/video asset processing — same pre-existing
  local `hachoir` package-mirror limitation noted in S4/S5, unrelated to S6;
  this phase's smoke pass used TXT/image/PDF per the stated machine
  limitation, plus MP3/MP4 code paths are entirely unchanged from S3.
